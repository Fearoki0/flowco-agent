P0-A — CENTRALIZE ALL COMMAND EXECUTION AND APPROVAL
======================================================================

Audit every path that can launch a process or shell command, including at minimum:
- exec_command()
- tool_run_command()
- tool_run_sandbox()
- tool_run_background()
- tool_start_server()
- tool_verify()
- tool_git()
- syntax_check() and helpers that launch interpreters/utilities
- PRoot and local execution paths
- every subprocess.Popen / subprocess.run / os.system / shell=True call

Create or strengthen ONE central execution policy/dispatcher. Every agent-invoked command must go through it and consistently enforce sandbox mode, command approval, applicable workspace/path restrictions, timeouts, process-group termination, and consistent exit-status reporting.

Requirements:
1. With confirm_commands=True, every command capable of arbitrary shell execution requires the same approval, whether foreground, background, server, verification, Git, or sandbox execution.
2. Non-interactive execution rejects unapproved commands unless a deliberately configured explicit approval policy exists. Never silently approve merely because stdin is unavailable.
3. FLOWCO_YES=1 and auto_confirm remain explicit opt-in overrides, never enabled by default; make their use visible in diagnostics.
4. A read-only subagent must not receive any tool capable of arbitrary command execution. Do not classify command-running verify as read-only.
5. Separate verification into safe file/syntax checks and command-based verification. Route the latter through the central dispatcher and approval policy.
6. Lower-level helpers must not permit another tool to bypass approval.
7. sandbox=off blocks every shell/process execution route, including verify, background jobs, servers, and sandbox scripts. Pure file inspection may remain available.
8. Timeouts and Ctrl+C terminate the entire child process group; do not leave zombies/orphans.
9. Use a consistent internal command result structure: stdout, stderr, exit code, timeout/interruption status. Adapt it to current UI at the boundary.
10. Test with mocked subprocesses and patched stdin; no test launches destructive commands.

Regression tests must cover: rejected foreground command; rejected background command; rejected server startup; rejected command-based verify; verify blocked when sandbox=off; destructive Git approval; non-interactive rejection by default; explicit FLOWCO_YES override only when set; process-group termination; and read-only subagents unable to execute commands.

P0-B — FIX run_sandbox SCRIPT PATH TRAVERSAL AND WRITE ORDER
======================================================================

Audit tool_run_sandbox() from input validation through script creation and execution.

Current risks to verify: script_name is joined to WORK/.sandbox/scripts and written before approval. A malformed filename may escape the intended directory, and approval currently occurs after writing.

Implement these protections:
1. Validate script_name before creating directories or files.
2. Accept only a simple filename, not a path. Reject absolute paths, separators, '.', '..', NUL bytes, control characters, traversal patterns, and unreasonable lengths. Allow only explicitly supported extensions (.py, .sh, .js) if still supported.
3. Resolve the final target and prove it remains under the canonical scripts directory using Path.resolve() and is_relative_to() (or a compatible helper).
4. Reject symlink-based escapes. Do not follow an attacker-created symlink to write outside scripts.
5. Never write script_code until required approval succeeds. Show the exact target and execution action for approval where practical.
6. Use atomic file creation/replacement; temporary files must remain inside the approved directory.
7. Ensure this tool cannot bypass the normal execution dispatcher.
8. Do not accept caller-controlled nested paths.
9. Rejected approval creates or modifies no script file.
10. Return clear errors without exposing secrets or environment values.

Add tests for a normal filename, ../ traversal, absolute filename, nested path, NUL/control characters, symlink escape, rejected approval leaving no file, no file created outside the temporary test workspace, and successful execution with correct output/exit code. Use TemporaryDirectory only; never write to real Android storage or system paths.

P0-C — BE HONEST ABOUT SANDBOX ISOLATION
======================================================================

Inspect actual guarantees of modes auto, proot, local, isolated, and off.

Setting cwd, HOME, TMPDIR, or PWD to WORK/.sandbox does not prevent a process from opening other readable/writable paths. It is workspace organization, not filesystem isolation.

Requirements:
1. Distinguish true OS-enforced isolation, PRoot containment and its limitations, workspace-scoped local execution with heuristic guards, and disabled execution.
2. Do not label a mode "isolated" or "secure sandbox" unless it enforces a real boundary verified on the supported platform.
3. If the current .sandbox mode only changes working directory/environment, rename it to an honest label such as "workspace" with backward-compatible config migration.
4. Update help, settings, status, tool descriptions, and README to describe actual guarantees.
5. If a genuinely isolated backend is requested but cannot be initialized or verified, fail closed instead of silently using unrestricted local execution.
6. Never claim PRoot is a perfect security boundary. Document limitations accurately.
7. Apply one execution policy to normal commands, background jobs, servers, verify, and sandbox scripts.
8. Prevent subagents/tools from changing sandbox mode or approval policy to bypass user consent.
9. If a mode cannot enforce the requested guarantee, reject it or explain the weaker alternative and require explicit user approval.

Tests must prove policy decisions and path/process behavior, not merely assert a function returns the word "isolated". If kernel-level isolation cannot be tested on Termux CI, state that limitation and do not claim it is proven.

P0-D — MAKE TOKEN BUDGET ENFORCEMENT CONSERVATIVE AND CONSISTENT
======================================================================

Audit BudgetManager and every model-generation/request path, at minimum:
- chat_stream()
- chat_plain()
- coder_complete()
- subagent chat calls
- cmd_testapi()
- cmd_stream_test()
- probe_model_capabilities()
- diagnostics/discovery functions that actually make model requests
- retries and stream fallback
- every direct urllib request to a model/completion endpoint

Requirements:
1. Create one central request gate that every billable/model-generation request passes immediately before dispatch.
2. No bypass based on streaming/non-streaming, main/subagent/coder/diagnostic, or mock/live mode.
3. Apply task and session limits consistently. Define whether diagnostics consume task budget; at minimum diagnostics obey session limits and appear in accounting.
4. Estimate input from the serialized request/messages (not just message content strings); include tool schemas and overhead where practical.
5. Reserve output based on the full configured max_tokens/max_completion_tokens limit. max_tokens is already a token quantity; do NOT divide it by four.
6. Reserve estimated usage before dispatch. Reconcile with actual provider usage after completion. Release or settle reservations carefully after failures depending on whether request transmission may have incurred cost; be conservative when uncertain.
7. Prevent concurrent callers from passing the same remaining allowance. Use a lock or equivalent reservation mechanism if concurrent model calls are possible.
8. Before every retry, verify the retry remains within budget. Retries may incur cost; account for them explicitly.
9. Normalize provider usage variants: prompt/input, completion/output, cached input, and reasoning tokens where available. Avoid double-counting cached usage.
10. Keep task, session, and provider scopes separate.
11. /budget add N extends only the active task cap. It must not reset usage, session ledger, or create a new task.
12. Validate and bound budget changes; prevent absurd/overflow values; keep config and BudgetManager consistent.
13. If reservation exceeds remaining budget, do not send the request. Explain the shortfall and extension mechanism.
14. Do not promise exact spending prevention when a provider doesn't expose exact usage or reservations cannot guarantee final billing. Explain estimates vs confirmed provider usage in /cost and /budget.
15. Mock requests use the same gate/accounting logic with deterministic usage and zero network access.

Critical issue to verify/fix: the current estimate resembles input_chars // 4 + max_tokens // 4. This under-reserves output because max_tokens is a token limit. Reserve the configured output allowance itself, or justify a different conservative rule from an enforceable provider-side cap.

Regression tests must cover: max_tokens=8192 reserves correct allowance; refused request sends no network call; task and session caps; diagnostics; coder calls; subagent calls; retries; cached usage without double-counting; task reset preserving session/provider totals; /budget add preserving usage; concurrent reservations; and test mode never reaching urllib/socket.

P1-A — FIX TASK CONTINUATION IDENTITY
======================================================================

Audit CONTINUATIONS, run_turn(), CURRENT task fields, BUDGET.start_task(), /budget add, REPL dispatch, and one-shot task mode.

Current risk to verify: global CONTINUATIONS and run_turn() use different aliases. "yes", "ok", or "keep going" may be handled inconsistently and reset task accounting.

Requirements:
1. Use one canonical continuation parser/helper everywhere.
2. Distinguish a real continuation from a new task. Do not treat every "yes" or "ok" as continuation when no paused/active task is awaiting one.
3. Continuation preserves task_id, task usage, remaining budget, plan/state, and conversation history.
4. A new task resets only task-scoped counters/state; preserve session/provider usage.
5. Never silently grant a fresh allowance when the prior task is paused or budget-exhausted.
6. Budget extension resumes the same task and preserves task ID.
7. Define/test behavior after success, interruption, API failure, and explicit /reset.
8. Do not misclassify genuinely new user requests solely because they begin with "yes" or "ok".

Test every accepted alias, new task after completed task, continuation after paused task, extension then continuation, and session-ledger preservation.

P1-B — FIX CONTEXT COMPACTION MESSAGE INTEGRITY
======================================================================

Audit compact(), slim_history(), message construction, and tool-call handling.

Current risk to verify: compact() retains a fixed number of trailing messages. It may split an assistant message containing tool_calls from its corresponding tool responses. Providers require tool responses to match assistant tool-call declarations and IDs.

Requirements:
1. Treat each assistant tool-call message and all corresponding tool responses as one indivisible history group.
2. Never retain a tool response without its preceding assistant tool-call declaration.
3. Never retain a tool-call declaration while dropping required tool responses, unless interrupted and every unfulfilled call receives a valid synthetic response.
4. Preserve system prompt at index 0.
5. Retain newest complete conversational groups, not an arbitrary count of individual messages.
6. Validate matching tool_call_ids, unique IDs, no orphan/duplicate responses, valid role/content shapes, and complete/pending state before sending.
7. Preserve active user request, task goal, plan, recent file changes, verified facts, and unresolved tool results.
8. Persist memory atomically. Do not silently swallow disk failures and claim memory was saved.
9. Keep context bounded, but prioritize valid groups over fixed count.
10. If valid compaction cannot be produced, keep previous valid history and report the problem. Never send malformed history.

Add tests with multiple tool calls; partial/all responses; interrupted calls; KEEP_FULL boundary; tool calls at boundary; long tool outputs; repeated compaction; memory write failure; and a validator rejecting orphan/duplicate responses.
