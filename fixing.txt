3. CRITICAL PRIORITY: REPAIR THE TOKEN BUDGET SYSTEM

This is one of the most important problems in the existing implementation.

Current implementation concerns:

- "USAGE" is global.
- The token budget is checked in the main agent loop.
- The subagent loop does not enforce the same budget.
- API retries can result in additional requests.
- The stream benchmark can consume tokens without updating normal usage statistics.
- Usage accounting needs to cover all model-calling paths.
- The budget-exhaustion message suggests that "continue" adds 100,000 tokens, but that behavior is not implemented.
- The current budget is effectively cumulative within a running process, rather than being cleanly separated into task and session accounting.

Completely redesign this system.

3.1 Separate usage accounting

Implement separate usage scopes:

Current task usage

- Tokens consumed by the current task.
- Tokens consumed by its subagents.
- Tokens consumed by retries.
- Tokens consumed by additional model calls.
- Tokens consumed by any separate coding model.

Session usage

- Total usage since the current FlowCo process started.
- Total number of API requests.
- Total successful and failed requests.
- Total retry attempts.

Provider usage

- Track consumption independently for each configured provider profile.
- Preserve usage history when switching providers during a session.

Do not mix task usage and session usage.

Starting a new task should initialize its task budget correctly without erasing session statistics.

3.2 Centralized budget manager

Create a centralized budget manager.

Every model request must go through it.

This includes:

- Main agent requests.
- Subagent requests.
- Coding model requests.
- Streaming requests.
- Non-streaming requests.
- Retried requests.
- Diagnostic model requests.

No model call should bypass budget enforcement.

The budget manager must perform a pre-request check.

Before making a request:

1. Estimate the incoming request token requirement.
2. Calculate the remaining task budget.
3. Reserve an appropriate output-token allowance.
4. Ensure the request does not knowingly exceed the configured limits.
5. Refuse or request user authorization when insufficient budget remains.

When actual usage arrives, reconcile the estimate with reported usage.

Do not present estimates as exact billing data.

3.3 Correct continuation behavior

Fix the broken continuation behavior.

When the budget is exhausted:

- Stop further API requests.
- Preserve the task state.
- Explain exactly why execution stopped.
- Display consumed tokens and remaining allowance.
- Offer an explicit way to extend the budget.
- Never automatically increase the budget.

Implement an actual command such as:

"/budget add 50000"

It must validate the requested value and require appropriate user confirmation.

Typing normal conversational text such as "continue" must not silently increase the budget.

3.4 Configurable spending limits

Provide:

- Maximum tokens per task.
- Maximum tokens per session.
- Maximum model requests per task.
- Maximum subagent requests per task.
- Maximum output tokens per request.
- Warning percentage.
- Maximum retry attempts.
- Optional estimated spending limit.
- Optional daily token limit.

All limits must be configurable.

Use conservative defaults appropriate for a user with a limited API allowance.

A configured limit must be enforced, not merely displayed.

3.5 Better token reporting

Support provider usage fields where available, including:

- "prompt_tokens".
- "completion_tokens".
- "input_tokens".
- "output_tokens".
- Cached input tokens.
- Cache-read tokens.
- Other provider-specific usage metadata.

Different providers return different usage structures. Build a normalization layer rather than assuming every provider follows exactly the same schema.

Track:

- Normal input tokens.
- Cached input tokens.
- Output tokens.
- Estimated tokens.
- Actual reported tokens.
- Unknown usage.

Do not count the same usage twice.

If usage is unavailable, estimate it and clearly mark it as estimated.

3.6 Cached token accounting

Add proper cached-token accounting.

Where supported, separately track:

- Normal input usage.
- Cached input usage.
- Output usage.

Allow configurable cached-input pricing.

Do not assume all providers offer cache discounts or report cache usage consistently.

The "/cost" command should calculate costs using the configured rates for the active provider.

Never invent prices.

When pricing is unknown, report that the cost cannot be reliably calculated.

3.7 Usage persistence

Consider a lightweight persistent usage ledger.

Requirements:

- Store usage locally.
- Keep provider usage separated.
- Keep task usage identifiable.
- Avoid storing API keys in usage records.
- Handle corrupted usage files safely.
- Avoid excessive disk writes.
- Allow the user to inspect and reset statistics explicitly.
